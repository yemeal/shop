# Памятка к защите проекта Shop API (Чистая Архитектура)

## 1. Короткое выступление на 60–90 секунд

> Я разработал модульный REST-бэкенд интернет-магазина на Node.js, Express 5 и SQLite, спроектированный по принципам **чистой слоистой архитектуры (Clean Architecture / Dependency Inversion)**.
>
> 1. **Слоистая архитектура:**
>    - **HTTP-слой (Контроллеры/Маршруты):** отвечает исключительно за прием запросов, прогон через middleware валидации схем и сериализацию DTO.
>    - **Сервисный слой (Бизнес-логика):** полностью изолирован от СУБД, не содержит ни строчки SQL-кода и зависит исключительно от абстракций интерфейсов репозиториев.
>    - **Слой репозиториев:** на каждую сущность (`User`, `Session`, `Address`, `Product`, `Category`, `Order`, `Favourite`, `Cart`) выделен свой абстрактный интерфейс (`I...Repository`), а доступ к SQLite вынесен в конкретные классы (`Sqlite...Repository`).
>    - **Абстракция транзакций:** заказы оформляются атомарно через абстракцию `ITransactionManager` (Unit of Work), скрывающую особенности `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`.
> 2. **Валидация и безопасность:**
>    - Все входящие `body`, `query` и `params` валидируются декларативными схемами.
>    - Ответы об ошибках строго стандартизированы: возвращают статус, машиночитаемый код (`code`), человекопонятное сообщение (`message`) и подробности (`details`), исключая утечку стек-трейсов или внутренних деталей СУБД клиенту.
> 3. **Безопасная аутентификация (RS256 JWT + Opaque Refresh + TokenFamily):**
>    - Вдохновлена промышленными решениями (включая микросервис Identity): stateless access-токен подписывается асимметричным ключом RSA (RS256, 2048 бит), передается в `HttpOnly` куке и валидируется публичным ключом.
>    - Refresh-токен — криптографически стойкая случайная строка (в базе хранится только SHA-256 хеш). На каждое устройство создается своя сессия со своей цепочкой токенов (`TokenFamily`).
>    - Поддерживается **ротация токенов** и защита от кражи токенов (**Reuse Detection**): при повторном предъявлении уже использованного токена вся сессия устройства немедленно аннулируется.
>    - Если access-токен просрочен, сервер через middleware **прозрачно обновляет пару токенов** по валидному refresh-токену без разлогинивания пользователя.
> 4. **Бизнес-сценарии:**
>    - Роли (`user` и `admin`), корзина в БД (`/api/cart`), фильтрация и поиск в каталоге, транзакционное создание заказов и избранное.
>    - Интерактивная OpenAPI/Swagger документация доступна на `/docs`.
>    - Все сценарии покрыты 8 наборами автоматических тестов (`npm test`).

## 3. Соответствие критериям оценки проекта

| Критерий | Как реализовано в проекте |
|---|---|
| **Архитектура и стек** | Четкое разделение на 4 слоя: Роуты -> Сервисы -> Абстрактные репозитории -> СУБД. Никакой логики в куче. Внедрение зависимостей (DI). |
| **Репозитории по сущностям** | На каждую из 8 сущностей есть `I...Repository` + реализация под SQLite. Сервисы не зависят от конкретной базы. |
| **CRUD-операции** | Каталог (чтение, добавление, обновление, удаление администратором), Категории, Заказы, Избранное, Корзина. |
| **Корзина (Cart)** | Таблица `cart_items` в SQLite. Атомарный `UPSERT (ON CONFLICT DO UPDATE)` исключает гонки при одновременных добавлениях. Привязана к пользователю, защищена от IDOR. При чекауте корзина очищается. |
| **Логинка, токены и куки** | **RS256 JWT Access + Opaque Refresh с TokenFamily**: Пароли хешируются с использованием `scrypt` с индивидуальной криптографической солью и защитой от timing-атак (`timingSafeEqual`). Access-токен подписан асимметричным ключом RSA (RS256, 2048 бит), живет 15 минут в HttpOnly cookie. Refresh — случайная 32-байтовая строка (opaque), в БД хранится только SHA-256 хеш. На каждое устройство создается своя сессия (`auth_sessions`) и цепочка токенов (`refresh_tokens`). При каждом обращении к `/refresh` происходит **ротация**. При обнаружении попытки повторного использования старого токена (**Reuse Detection**) вся сессия немедленно отзывается. Если access просрочен, middleware **прозрачно обновляет токены** по refresh-куке. |
| **Админка и роли** | Роли `user` и `admin` в таблице пользователей. Middleware `requireRole('admin')` защищает операции создания/редактирования товаров, категорий и смены статуса заказов. Защита от IDOR блокирует доступ пользователей к чужим корзинам, заказам и избранному. |
| **Валидация полей** | Модуль `src/schemas/validator.js` проверяет типы, границы, уникальность элементов, корректность email. Валидируются все входящие схемы, включая создание категорий. |
| **Формат ошибок** | Строгий контракт `{ error: { code, message, details } }`. При 500 ошибках детали и стек-трейсы скрываются от клиента. Нарушения ограничений БД мапятся в безопасный код `DATABASE_CONSTRAINT`. |
| **Транзакции в БД** | Заказ и позиции создаются атомарно внутри `SqliteTransactionManager` (`BEGIN IMMEDIATE` -> `COMMIT`/`ROLLBACK`) с очередью промисов для безопасной параллельной работы с SQLite. |

## 5. Тестирование

```powershell
npm test
```
Запускает встроенный раннер Node.js (`node --test`), проверяя:
1. Сквозные сценарии интернет-магазина (каталог, категории, транзакционный заказ, избранное).
2. Соответствие репозиториев абстрактным интерфейсам (`instanceof I...Repository`).
3. Валидацию данных и машиночитаемый формат ошибок (`VALIDATION_ERROR`, `RESOURCE_NOT_FOUND`).
4. Авторизацию, куки, токены и разделение доступа (админка: `403 FORBIDDEN` vs `201 CREATED`).
5. Полный цикл работы с корзиной (добавление, изменение, чекаут и очистка).
6. Защиту от IDOR и безопасность транзакций (изоляция пользователей, хеширование scrypt, предотвращение параллельных коллизий SQLite).
